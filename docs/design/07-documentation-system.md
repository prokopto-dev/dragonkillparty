# Documentation system

**Status:** design. **Audience:** contributor, agent. The docs tree exists; the site, the linters and
the gates do not. This document specifies them and names what the owner cut from 1.0.

Documentation for a self-hostable product must itself be self-hostable, forkable and readable with no
internet connection, because the person who needs it most is an officer whose box is offline and whose
web UI is broken. Every decision below is downstream of that.

## Decisions at a glance

| Question | Decision | Reason |
|---|---|---|
| Framework | Diátaxis for navigation, audience as a second axis expressed in frontmatter and four link-lists | Role-sharded trees duplicate content; need-shaped trees do not |
| Generator | **Astro + Starlight** (MIT), plain CommonMark content | No new toolchain, and frontmatter is zod-validated, which makes the anti-verbosity rules a build error rather than a style guide |
| Source of truth | `docs/` in this repository, one copy, embedded in the binary | No wiki, no Notion. The docs at a tag are the docs that shipped. |
| Versioning | Tag-built, path-deployed (`/v1.4/`) | No `versioned_docs/` snapshots for an agent to edit by mistake |
| Hosting | Cloudflare Pages primary, GitHub Pages documented as a mirror | Per-PR previews; docs URLs are compiled into shipped binaries and need a redirect map |
| Search | **Pagefind** on the site, a flat JSON index in the binary | An Algolia dependency makes the offline copy's search dead — and the offline copy is the one that matters |
| API reference | Huma → `openapi/openapi.json` → **Scalar**, the same bundle on the site and in the binary | MIT, OpenAPI 3.1 with `webhooks`, a working request console, static build, no CDN |
| Spec linting | `vacuum` in `make check`, `oasdiff` for breaking changes | Render with one tool, lint with another |
| Prose linting | **Vale**, Google base style plus a project vocabulary | A Go binary, no runtime; substitutions enforce the project's vocabulary |
| Link checking | **lychee** over built HTML | Broken links are the highest-frequency docs defect |
| ADRs | MADR 4 minimal, `docs/adr/NNNN-*.md`, **published** | "Why no Postgres?" gets a link, not an argument, for the twentieth time |
| Screenshots | Generated by Playwright at docs-build time, **never committed** | Zero binary churn in git, zero rot; a missing screenshot is a red build |
| Agent entry point | `AGENTS.md` only; the docs own the long-form references it links to | Constraints in the repository, look-ups on the site |

**Rejected, with reasons:**

| Rejected | Why |
|---|---|
| **Docusaurus** | In-core versioning writes snapshot copies of the whole tree into the working directory — directly hostile to "docs change in the same PR" (which copy does the PR edit?) and to grep-based agent navigation. MDX by default breaks the goldmark renderer inside the binary. |
| **VitePress** | No versioning story at all. |
| **MkDocs Material** | The best defaults of the five, but it adds a **Python toolchain** to a Go and TypeScript repository: a third lint, test and CI loop for a volunteer maintainer. `mike` versioning is a third-party plugin anyway. |
| **Mintlify** | Proprietary SaaS. The documentation for a self-hostable, permissively-licensed product must be self-hostable and forkable, and it cannot be embedded in a binary. |

## Information architecture

### Two axes

Navigation is **need-shaped** (Diátaxis). Discovery is **audience-shaped**. Every page carries an
`audience` list in frontmatter; the four "start here" link-lists in `docs/README.md` are filtered by
it and contain **no unique content**. That is the only way to serve five audiences without writing the
same install instructions three times.

| Audience | Learning | Doing | Looking up | Understanding |
|---|---|---|---|---|
| Guild member | Claim your character | Balance, dispute, bid, sign up | Glossary, attendance, statement columns | Why balances are derived; person versus character |
| Officer | First raid night; set up a point system | Ticks, awards, bids, decay, reconciliation, ranks | Strategies, parser grammars, permissions | Attendance model; decay; bid sessions; differences from EQdkp Plus |
| Admin / self-hoster | Migrate from EQdkp Plus | Install, HTTPS, backup, upgrade, doctor, tokens | Configuration, CLI, doctor checks, backup format | Security model; what we import and why not |
| Bot developer | Build a Discord bot | Auth, pagination, idempotency, errors, webhooks, SSE, ingest, port a bot off `api.php` | OpenAPI, error catalogue, scopes, webhook events, compat shim | API design rationale; the no-superadmin rule |
| Contributor / agent | — | Local dev, add a strategy, add a parser, add an endpoint, release | Invariants, architectural laws, test taxonomy, generated-file inventory | ADRs |

Two deliberate asymmetries. **Contributors get no tutorial quadrant** — they get
`internal/api/EXAMPLE_ENDPOINT.md`, a worked in-repo example, which is strictly better than a
narrative. **Members get almost no explanation quadrant** — a raider reading documentation is annoyed
about a number and wants the answer, not the philosophy.

### The tree

The in-repo layout is flat under `docs/`, not nested under `docs/content/`. Directory names are the
Diátaxis quadrants in the reader's language, so the URL says what the page is for:

```
docs/
├── README.md                the hub: four audience link-lists over the tree
├── getting-started/         learning: install and first run
├── guides/                  doing: officer and member tasks
├── concepts/                understanding: ledger, strategies, invariants, glossary
├── operations/              doing: configuration, upgrade, troubleshooting
├── migration/               doing: leaving EQdkp Plus
├── api/                     doing: auth, idempotency, pagination, realtime
├── integrations/            doing: build a bot
├── development/             doing: contributor tasks
├── reference/               GENERATED — never hand-written
├── design/                  the specification, for contributors
├── adr/                     decisions, published
├── embed.go                 //go:embed all:...  — the binary's copy
├── EMBEDDED.txt             allow-list of paths the binary ships
├── site/                    the Astro + Starlight project
└── styles/                  Vale styles and vocabularies
```

`docs/` is a Go package so the binary embeds the canonical markdown with no copy step and no second
source of truth.

> Source contradiction, resolved here: the original design proposed `docs/content/` with
> `start/ tutorials/ guides/ reference/ explanation/`. The repository uses the flat layout above.
> This document is authoritative for the layout; the older proposal is stale.

### What the binary embeds

Not the whole site. `EMBEDDED.txt` allow-lists `reference/**`, `operations/**`, `getting-started/**`,
`concepts/glossary.md` and the troubleshooting pages — roughly 400 KB of markdown, rendered at `/docs`
by goldmark with the same navigation tree.

Three tests guard it:

| Test | Limit |
|---|---|
| Embedded subset size | ≤ 1 MB uncompressed |
| Image references in the embedded subset | Zero |
| Internal links in the embedded subset | Resolve inside the subset, or are rewritten at embed time to absolute `https://docs.dragonkillparty.org/…` URLs |

The embedded copy exists for the admin whose box has no outbound internet and whose SPA bundle is
broken. That population needs troubleshooting and the CLI reference, and does not need screenshots.

## Versioning

Path-based, built from tags, one path per **minor**.

```
docs.dragonkillparty.org/        current stable (canonical)
                        /v1.3/   frozen, built from the tag
                        /next/   main; noindex; banner; nothing may link to it
                        /versions.json   drives the switcher
```

| Rule | Detail |
|---|---|
| Build | The release workflow checks out `v1.4.2` and builds with `--base=/v1.4/`. Patch releases republish in place. |
| Retention | Current plus three previous minors in the switcher; older versions stay reachable |
| Banner | Old versions carry "You are reading the 1.1 documentation; the current release is 1.4", linking the same slug |
| Canonical tag | Versioned pages point `rel=canonical` at the current-version URL |
| `/next/` | `noindex`, and a build check fails any link to it |

**Docs URLs are a public API.** RFC 9457 `type` URIs and `dkp doctor` output are compiled into binaries
that will still be running in 2029. A test compares the built sitemap against the previous release's
and fails on any removed path without a `_redirects` entry.

**Unversioned forever:** `/errors/<code>` and `/ops/checks/<id>` are served from the root, because an
18-month-old binary links to them. Version-specific behaviour appears as a "Changed in 1.4" note inside
the page. This exception is written into the redirect-map test.

Why not in-repo snapshot directories: they duplicate the entire tree into the working directory, which
breaks the same-PR rule, makes every grep ambiguous, triples the repository's markdown, and is a
reliable way for an agent to edit a frozen snapshot instead of the live page. Building from the tag
gives a stronger guarantee with one copy — **the docs at a tag are the files the binary embedded.**

## Search

| Surface | Mechanism |
|---|---|
| Public site | Pagefind, built after Astro over the generated HTML. `data-pagefind-weight` boosts titles, descriptions and `<code>` spans, so searching `DKP_AUTO_MIGRATE` or `insufficient_balance` lands on the right page. Filters exposed for `audience` and `diataxis`. |
| The API reference gap | Scalar renders client-side, so Pagefind cannot index operations. `reference/api-operations/<tag>.md` is generated from `openapi.json` — one static page per tag listing every operation with its summary, path, scopes and error codes, deep-linking into Scalar. Without it, searching `createRaidTick` finds nothing, which is the most likely search a bot author types. |
| Inside the binary | A build-time `search-index.json` — title, headings, description, first 200 characters per page — plus a 3 KB prefix filter. Worse than Pagefind, about 100 KB instead of a WebAssembly runtime, and it works in a `FROM scratch` image with no network. |

## API reference

```
Go handler types ──huma──► openapi/openapi.json (committed, CI diff-gated)
                             ├─► Scalar bundle → /reference/api (site) and /docs/api (binary)
                             ├─► reference/api-operations/*.md   (searchable static index)
                             ├─► reference/webhooks.md, scopes.md, permissions.md
                             ├─► clients/ts, clients/python
                             └─► vacuum lint + oasdiff breaking-change gate
```

Four gates:

| Gate | Fails when |
|---|---|
| Spec regeneration | `openapi.json` regenerated in CI differs from the committed copy — so a handler change without a spec update is impossible |
| `vacuum` | An operation lacks an explicit `operationId`, a summary of ten characters or more, a description, at least one example per request and response schema, or a `Security` entry. **Spec documentation quality is a lint failure, not a review comment.** |
| `oasdiff` | Any breaking change without an explicit label and a `reference/api-changelog.md` entry |
| Error-page coverage | A Go test asserts every code in the closed error enum has a `reference/errors/<code>.md`; an Astro check asserts no orphan error pages exist |

**Renderer: Scalar.** MIT, renders OpenAPI 3.1 including `webhooks`, ships a static build, and includes
a request console with no paywall — vendored, not loaded from a CDN, and used in both places, so an
admin with no outbound internet gets the same reference as the public site. Redoc was the close second
on typography, but its "try it" console is a paid feature and a first-class API is the product thesis:
the reader must be able to fire a request. Redocly CLI stays as a second linter in the nightly job.

### Examples that provably work

**No code block in prose is typed by a human into a markdown file.** Every example is a file,
transcluded:

| Mechanism | Behaviour |
|---|---|
| `docs/site/src/plugins/remark-snippet.mjs` | Expands ` ```bash file=openapi/snippets/create-tick.sh region=request `. A missing file or region fails the docs build. |
| `test/integration/snippets_test.go` | Executes **every** file in `openapi/snippets/` against an `httptest` server seeded with the canonical fixture guild and asserts the expected status. Outputs are golden files under CODEOWNERS; `-update` is banned in CI. |
| Determinism | One canonical fixture — guild "Sanctum of the Sleeper", server Blue, era Velious — with stable ULIDs. Every example uses `$DKP_BASE_URL` and `$DKP_TOKEN`, so a reader who exports two variables can paste any snippet. |
| SDK examples | Compiled and smoke-tested in CI, then transcluded. Because SDK method names derive from `operationId`, and `operationId` is explicit and uniqueness-tested, a renamed handler cannot silently rename a documented method. |

The quickstart is an end-to-end test and `examples/discord-bot/` is a built project, so the three
highest-traffic documents in the project are executable.

## Prose linting

Vale, with `Google` as the base plus `docs/styles/DragonKillParty/`. Error-level rules block; warnings
annotate.

| Rule | Value |
|---|---|
| Person | Second person. "You create a pool." Never "the user", never "we" outside `concepts/` |
| Mood | Imperative for steps: "Open Settings", not "You should open Settings" |
| Tense | Present. "The importer writes a report", never "will write" |
| Voice | Active. Passive constructions above three per page are flagged |
| Sentence length | ≤ 25 words warns, ≤ 35 errors |
| Paragraph length | ≤ 4 sentences |
| Headings | Sentence case. Gerunds allowed in task titles, banned in reference titles |
| Banned words | simply · just · easy · easily · obviously · of course · powerful · seamless · robust · blazing · revolutionary · leverage · utilize · in order to · please note that · it should be noted · basically · essentially |
| Banned punctuation | Exclamation marks. Emoji anywhere in `docs/` |
| Link text | Descriptive. "here", "this link", "read more", "click here" are errors |
| Numbers | ISO 8601 dates, UTC unless stated, `24 MB` with a space, ranges with an en dash |
| Formatting | UI labels bold, paths and identifiers in code, keys in `<kbd>` |
| Openings | No page begins by restating its title. No heading named Introduction, Overview, Background, Conclusion or Summary |

**The naming rule that matters more than it looks:** the product is **Dragon Kill Party**; the concept
is **dragon kill points (DKP)**; the CLI is `dkp`. Never write "DKP" as the subject of a sentence about
the software. Vale flags "DKP is", "DKP can", "install DKP", "DKP's". Getting this wrong makes every
sentence in the manual ambiguous to a reader who is already unsure what points are.

Substitutions enforce the vocabulary: `toon → character` outside the glossary, `mob → encounter` in
reference pages, `raid → raid session` where the entity is meant. The project vocabulary keeps
`Velious`, `Kunark`, `Iksar`, `Trakanon`, `mysqldump`, `centipoints`, `ULID` and `goldmark` from
tripping the spell check.

## Link checking

lychee over the built HTML. **Internal links block on every PR; external links run nightly only**, so a
third-party site going down never blocks a merge. Broken internal links are the highest-frequency
documentation defect and the cheapest to catch.

## Screenshots

**Automated with Playwright — after cutting the number of screenshots by 80%.**

| Rule | Detail |
|---|---|
| Permitted only where the UI is the subject | First-run wizard, importer dry-run report, reconciliation queue, live bid board, ledger statement, saved table views. Maximum three per page. |
| Never screenshot | Terminal output (a code block is copy-pasteable and searchable), configuration (a table), API responses (JSON), or **error messages** — a user searching for their error must hit text, not a PNG |
| Generation, not capture | `docs/site/scripts/screenshots.spec.ts` boots the released binary against the canonical fixture volume, pins viewport, clock, locale and animations, and captures each named shot in light and dark |
| Nothing is committed | No images in git. They exist only in the built site, which makes screenshot rot **structurally impossible** — every published image came from the code in that same build. |
| Missing shot | `<Screenshot name="first-run-wizard" alt="…"/>` **fails the build** if that shot was not produced by this run. A renamed route breaks the docs build loudly instead of silently publishing a stale image. |
| Alt text | A required prop; Vale checks it is not "screenshot of the dashboard" |

Honest costs: the capture script needs maintenance when navigation changes, and the docs build now
depends on a built binary, adding about 90 seconds to the release docs job. Both are cheaper than
hand-managed screenshots in a volunteer-maintained project.

## Anti-verbosity as a build error

`docs/site/scripts/check-budgets.mjs` runs on every PR. Prose words exclude code fences, tables,
frontmatter and transcluded snippets. The frontmatter schema in `src/content.config.ts` is a zod
schema, so these are structural requirements rather than a style guide nobody reads.

| Constraint | Limit | Level |
|---|---|---|
| Reference page | ≤ 400 prose words | error |
| Task page (`guides/`, `operations/`, `api/`, `development/`) | ≤ 600 | error |
| Learning page (`getting-started/`) | ≤ 1,200 | error |
| Understanding page (`concepts/`) | ≤ 1,500 | error |
| FAQ answer | ≤ 3 sentences | error |
| ADR (`docs/adr/`) | ≤ 1,000 words, whole file — the ceiling `0000-template.md` states | error |
| Heading depth | `###` maximum | error |
| H2 count | ≤ 7 per page | warn |
| `description` frontmatter | required, ≤ 160 characters, must not restate the title | error |
| First code block or table | within the first 30 lines of a task page | error |
| Banned headings | Introduction · Overview · Background · Conclusion · Summary · Getting Started as an in-page heading | error |
| Banned openings | A first sentence restating the title; "In this guide, you will learn…" | error |
| Title contains "and" | — | warn — one concept per page |
| Link-only pages | forbidden except `docs/README.md` and the section indexes | error |
| Terms defined in-page that exist in the glossary | link instead | warn |
| Embedded subset total | ≤ 1 MB | error |

**One concept per page** is enforced socially by the "and" warning and structurally by the word
budget: a page covering two things cannot fit in 400 words, so the budget does the arguing.
**Examples over prose** is enforced by the first-30-lines rule. **Tables over paragraphs** cannot be
linted; it is review item 6 below, and the reviewer's licence is that any list of three or more items
with two or more attributes must become a table or the reviewer converts it.

Design documents in `docs/design/` are exempt from the word budgets and subject to everything else.
They are a specification for contributors, not a manual.

### Review checklist

A section of `.github/PULL_REQUEST_TEMPLATE.md`:

1. Does the title say what the reader will be able to do, in the reader's words?
2. Can the first sentence be deleted without loss? If yes, delete it.
3. Is this one concept? If the page needs an "and", split it.
4. Is it in the right quadrant? Steps in a reference page and explanation inside a task page are the
   two commonest defects.
5. Is every claim about behaviour backed by a snippet, a generated table, or a test?
6. Is any paragraph actually a table?
7. Does every code block come from a transcluded file rather than a keyboard?
8. Would a reader who has never played EverQuest understand it? One who has never used Docker?
9. More than three "next steps" links? Cut to three.
10. Does a screenshot exist that a table or code block would say better?
11. Does anything here duplicate another page? Link instead — duplication is the root cause of every
    stale document.
12. Are the error strings byte-identical to what the software emits?
13. Are new terms in the glossary and the Vale vocabulary?
14. Does the URL need a redirect entry, and is one there?
15. Read it aloud. Any sentence you stumble on is over 25 words or passive.

## The docs gate

A blanket "code changed, so docs must change" check gets rubber-stamped within a month. Split it into a
**mechanical half with teeth** and a **judgement half with a counted escape hatch**.

### Mechanical — no escape hatch

These are diff checks, not nags. The "docs update" is `make gen`, which regenerates the
`docs/reference/` tree alongside every other generated artefact — there is one regeneration command,
and it is in the canonical table.

| Trigger | Check |
|---|---|
| New or changed `DKP_*` field | `reference/configuration.md` regenerates identically |
| New or changed Cobra command or flag | `reference/cli/*` regenerates identically |
| New error code | `reference/errors/<code>.md` exists with a non-placeholder body |
| New strategy id | `reference/strategies/<id>.md` exists and its `ConfigSchema` block matches |
| New webhook event | Present in `reference/webhooks.md` |
| New or changed route | `scopes.md`, `permissions.md` and `api-operations/` regenerate identically; summary and description non-empty |
| New doctor check | `reference/ops-checks/<id>.md` exists |
| New parser format | `reference/log-formats.md` includes it, with a golden excerpt |
| New importer table mapping | `reference/eqdkp-mapping.md` regenerates identically |

### Judgement — one escape hatch, counted

A `docs-gate` job fires only when the diff touches `internal/api/**`, `internal/config/**`,
`internal/strategy/**`, `internal/importer/**`, `cmd/dkp/**`, `db/migrations-*/**`, `deploy/**` or
`openapi/openapi.json`. It passes on any of: a change under `docs/`; a `docs: <what changed>` line in
the PR body; a `docs: n/a — <reason>` line; or the maintainer-only `no-docs-needed` label.

**The reasons are harvested weekly into a report.** An escape hatch that is counted is an escape hatch
that gets used honestly.

Also on every PR: Vale on changed markdown, lychee on internal links, the frontmatter schema, the
budget checker and the redirect-map test.

## In-product documentation

Treated as part of the docs surface, with CI links so it cannot drift.

| Surface | Contract |
|---|---|
| Error bodies | RFC 9457 `type` is `https://docs.dragonkillparty.org/errors/<code>`, unversioned and permanent. Each error page has four sections and nothing else: what it means (one sentence), the most common cause, how to fix it, and what a bot author should do programmatically. |
| `dkp doctor` | Prints `→ https://docs.dragonkillparty.org/ops/checks/<id>` after each failed check; `/ops` renders the same as a link. Migration refusals print the exact recovery command *and* the guide URL. |
| Contextual help | `web/src/help/registry.ts` maps `helpKey → {slug, anchor}`. Components take a `helpKey`, never a URL. A build-time test resolves every key against the docs sitemap, so a moved page fails the SPA build. In-app help copy is capped at 140 characters; anything longer becomes a page and a link. |
| Empty states | Every collection view ships one sentence saying what this is, one primary action, one docs link. Two variants where it matters — fresh install and import in progress — because an officer staring at an empty roster during a four-minute import is the moment they file a bug. |
| First-run wizard | Six steps, copy written once and reviewed as documentation, living in `internal/ops/templates/`. Every step has a one-line "what happens if I skip this" and no step has more than three fields. |

The Go test enumerating the error enum against the docs tree makes an undocumented error impossible to
merge; the Astro check makes an orphan page impossible.

## Architecture decision records

**MADR 4 minimal**, `docs/adr/NNNN-kebab-title.md`, published on the site under Decisions. Sequential
four-digit numbers; on a merge conflict the later PR renumbers.

Required sections: Status (`proposed | accepted | superseded by NNNN | deprecated`) · Context (≤ 5
sentences) · Decision · **Considered options** (at least two, each with a one-line advantage and
disadvantage) · Consequences split into positive and **negative** · **Reversal cost**, one line on what
undoing this costs in two years.

Two of those carry the weight. **An ADR with no negative consequences is rejected in review**, and the
reversal-cost line is what a future maintainer actually needs.

| | When |
|---|---|
| **Required** | A change alters a public contract (API shape, wire format, CLI, config keys, backup format); adds a runtime dependency, process, port or volume; changes a data-model invariant or a ledger rule; picks between two viable libraries; takes more than about two weeks to reverse; or answers a question a reader would otherwise re-litigate |
| **Not required** | Ordinary features, refactors, bug fixes, new pages, or adding a strategy or parser that fits the existing interface — that is the interface working as intended |

**Enforced:** `ADR001` in `scripts/repo-gates.sh`, in the `lint / repo` job. A PR that adds a new
*direct* requirement to `go.mod`, touches `deploy/Dockerfile` or `db/schema.hcl`, or adds a top-level
`internal/` package requires either a new file under `docs/adr/` or an `adr: n/a — <reason>` line in
the PR body — with a reason, since harvesting it is the point. Same harvest-the-reasons discipline as
the docs gate. The `go.mod` trigger compares direct requirements against the base revision, so a
version bump does not fire; the `deploy/Dockerfile` and `db/schema.hcl` triggers are the path itself,
because "new port, volume or process" and "new table or changed constraint" are judgements no grep
can make and the cost of asking is one line. It runs on pull requests only — the body is its input —
and `ci.yml` passing that context is pinned by a test, because this paragraph asserted enforcement
for months while none existed.

Published rather than hidden, because "why is there no Postgres option?" and "why did you not fork
EQdkp Plus?" will otherwise be re-asked in every issue thread for two years. See
[the index](../adr/README.md).

## Documentation for agents

### The split with `AGENTS.md`

> `AGENTS.md` contains what must be true **before** the agent writes a line of code. The docs contain
> what the agent should **look up**. Anything in `AGENTS.md` that grows past about 20 lines moves to a
> docs page and leaves a one-line pointer.

`AGENTS.md` keeps the four architectural laws with their mechanisms, the canonical command table with
expected wall times, pinned versions and the exact library idiom in use, the licence firewall, and
pointers to `internal/api/EXAMPLE_ENDPOINT.md` and `db/RECIPES.md`. The docs own
`reference/invariants.md`, `reference/configuration.md`, `reference/errors/`,
`reference/strategies/`, `reference/scopes.md`, [Architecture overview](../development/architecture-overview.md)
and the ADR index.

### What an agent needs that a human does not

| Need | Why a human does not need it | Where it lives |
|---|---|---|
| Invariants stated as assertions **with the mechanism named** | Humans infer intent from surrounding code | `reference/invariants.md`, summarised in `AGENTS.md` |
| Forbidden patterns as a table **with the observable symptom** | Humans avoid them by taste | The `AGENTS.md` failure-mode table |
| Canonical commands with expected wall times | Humans have shell history | `AGENTS.md` |
| A task → file routing table | Humans grep cheaply; agents burn context | [Architecture overview](../development/architecture-overview.md) |
| Worked in-repo examples rather than API prose | Humans read library documentation | `EXAMPLE_ENDPOINT.md`, `db/RECIPES.md` |
| "Generated — do not edit" headers plus the regeneration command | Humans notice the header | Every generated file |
| **Negative space** — what is deliberately absent | Humans do not add a Redis unprompted | The ADR index and `AGENTS.md` |
| A licence firewall statement | Humans do not paste AGPL PHP when asked to match behaviour | `AGENTS.md`, `CONTRIBUTING.md`, the PR template, a CI grep |

The inverse matters equally: humans need motivation, trade-offs and history, which is what `concepts/`
and the ADRs are for, and which an agent should mostly not be loading. Human documentation answers
"why"; agent documentation answers "where, exactly, and what will break".

### Agents building bots

A distinct and under-served audience. If the API is the extension point, an agent writing a guild's
Discord bot is a first-class reader.

| Artifact | Purpose |
|---|---|
| A single page containing the whole client contract | Auth and scopes, the idempotency rule, cursor pagination and `since_seq`, `If-Match`, the RFC 9457 error shape, the SSE contract with its `resync` behaviour, webhook signature construction. Written to be pasted whole into a context window. |
| `llms.txt` | An annotated index, generated at docs build |
| `openapi.json` served unversioned on **every instance** | So an agent fetches the *reader's own* spec rather than a possibly newer published one. The instance's spec is the truth for that instance. |

| The second, binary-embedded search index | **No** | Yes |
| `llms-full.txt` | **No** — `llms.txt` only | Yes |
| Playwright screenshot generation | **No** — no screenshots at 1.0 | Yes |

The consequence of deferring versioning is acceptable precisely because the binary embeds its own
docs: a 1.1 instance serves 1.1 documentation from itself even when the public site has moved on.

## Build order

1. **Skeleton and gates first, content second.** The site scaffold, the frontmatter schema, the budget
   checker, Vale, lychee, the redirect test and the generators. Establish constraints before there is
   content to grandfather in — the same reasoning as building the API CI gates before there are routes.
2. **Generators.** Configuration, CLI, errors, strategies, webhooks, scopes, invariants, EQdkp mapping.
   Roughly half the reference tree is then free and permanently correct.
3. **The three executable documents.** The quickstart as an end-to-end test, the snippet suite, and
   `examples/discord-bot/`.
4. **Admin guides.** Install, HTTPS, backup and restore, upgrade, migrate. This set decides whether
   guilds can adopt at all.
5. **Officer guides.** The raid-night procedure and the point-system decision table.
6. **Troubleshooting and error bodies**, written from real alpha failures rather than invented.
7. **Concepts and the ADR seed set**, written last from what already exists.
8. **Member pages and the FAQ** last — the shortest, and dependent on everything else being linkable.

## Ownership

Documentation is not a separate role. The person or agent changing behaviour changes the page, the gate
enforces it, and the maintainer reviews prose with the checklist above.

Two health metrics, reported weekly from CI: the count of `docs: n/a` escape hatches used, and
operation coverage (documented operations ÷ total operations). Neither is a target. A change in either
is a signal.
